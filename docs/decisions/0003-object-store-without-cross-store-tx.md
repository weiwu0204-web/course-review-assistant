# 0003：无跨存储事务下先落盘不可变对象再发布数据库引用

- **状态**：已采用
- **日期**：2026-11-26（源自 [ADR 0001](0001-service-preview.md) 与 [001 设计](../specs/001-courseware-revision/design.md)）

## 背景与约束
服务版将原始课件、试题、章节生成产物和知识库分块存放在私有对象存储（SeaweedFS S3 / 本地对象目录），而权限归属与版本号存放在 MySQL。关系型数据库与对象存储之间不存在原生原子分布式事务。

## 决策
所有写路径统一采用**不可变对象键 + 先写对象、后提交数据库引用**的顺序：
1. 每次版本发布或每次 worker 生成尝试均分配全新的唯一对象键（底层存储拒绝同键覆盖写入）。
2. 先将完整字节流写入对象存储并确认成功，再开启数据库短事务做乐观基准版本校验（`base_revision`）或领取标记校验并写入引用行。
3. 若数据库提交因已知并发冲突（409）或校验失败回滚，立即尝试删除刚刚上传的未引用对象；若提交结果未知（如网络闪断），保留对象留待离线对账，**绝不清理任何已被数据库引用的历史版本对象**。

## 备选方案与取舍

| 候选方案 | 优势 | 放弃原因 |
|---|---|---|
| **不可变键 + 先对象后元数据（选定）** | 外部读者永远不会读到“数据库有记录但对象不存在/写了一半”的损坏状态；天然保留历史版本供在途任务使用 | 极端崩溃下可能残留少量未被引用的孤儿对象 |
| 先写数据库记录再传对象 | 不会产生未登记对象 | 上传中断或耗时期间会出现悬空引用，并发读取与回滚处理更脆弱 |
| 原地覆盖同名对象键 | 节省存储空间 | 破坏已提交批任务与旧知识库的输入版本固定承诺，回滚即丢失旧版内容 |

## 后果与演进触发条件
- **正面收益**：已发布版本只读不可变，并发更新冲突时既有版本 100% 完好；升级回滚无需搬迁对象数据。
- **代价与残余风险**：需要后续配套低频孤儿对象巡检清理工具（列入 [路线图](../roadmap.md)）。
