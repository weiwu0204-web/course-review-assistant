# P3 设计稿 · 课程知识库（RAG + 流式 + 引用溯源）

> 日期：2026-10-15 ｜ 前置：P1 覆盖率可见化（v0.8.9）、P2 verify→repair 闭环（v0.8.12）
> 一句话：把「生成一次性文档」升级为「**可反复追问的课程知识库**」，
> 并在 RAG 上做一件别人不做的事——**引用不只是有，而是可验证**。

---

## 0. 为什么做这个（不是别的）

1. **简历上的三格空缺**：RAG / 流式 / 引用溯源——对照项目二（企业级面试平台）的缺口清单，
   主项目（原创、能扛追问的那个）恰好缺这三项。P2 补上了工具调用与收敛控制，这三项是剩下的。
2. **真实痛点**：生成的复习文档解决了"翻完所有 PPT 太慢"，但没解决
   "我记得第 7 页有个参数，它到底是什么意思"——这是**追问**，不是重读。
   一次性文档答不了追问，知识库能。
3. **★ 差异化在这里**：市面上的 RAG 项目都在证明"我有引用"。
   **本项目已有的 term 级抽取能力（`coverage.py`）可以做"引用可信"** ——
   用答案里出现的术语去比对被引用页的原文，自动判定这条引用站不站得住。
   **把 P1/P2 建的"可验证"能力，从"内容有没有漏"扩展到"引用有没有编"。**

## 1. ★★ 先量再改：检索层选型的实测依据

> 本节是**本轮新增**，它推翻了原规划的一处前提。数据来自 `scripts/p3_probe.py`
> （`output/_p3_probe.json`），语料 = 仓库里 14 份真实 Ceph 课件。

### 1.1 原规划的前提不成立

原规划写的是：

> 先用 numpy 暴力余弦（零依赖）→ 再引入向量库（`sqlite-vec`）做性能对比

**这段话有个隐藏前提：先得有 embedding 向量。** 而实际情况是——
本项目的四家 provider（DeepSeek / 智谱 / Kimi / 通义）配置里**全是 chat 模型，
一个 embedding 配置都没有**（见 `app/config.py` 的 `AI_PROVIDERS`）。
DeepSeek 干脆没有 embedding API。所以"用不用向量库"是个伪问题，
真问题是：**这个语料 + 这个规模，到底需不需要神经 embedding？**

### 1.2 实测数据（325 个 chunk，14 份真实课件）

| 指标 | 实测值 |
|---|---|
| 语料规模 | 14 份课件 → **325 个 chunk**（按页切）｜总 **7.8 万字符**｜词表 11,182 |
| chunk 字符数 | min 11 / p50 186 / p90 532 / max 690 |
| 索引构建耗时 | **11 ms** |
| **查询延迟** | **p50 0.20 ms / p95 0.43 ms**（暴力全量打分，**无 ANN 索引**） |
| 术语 query 召回@5 | **98.8%**（英文 98.5% ｜ 数字/单位 100% ｜ 纯中文 100%） |
| 口语 query 召回@5 | **92.9%** → **查询改写后 100%** |

### 1.3 四条结论（每条都有对应的"所以不做什么"）

| 结论 | 依据 | 决定 |
|---|---|---|
| **不需要向量库** | 全量暴力打分 **0.20 ms**。ANN 索引解决的是"百万级文档下检索太慢"，这里差着三四个数量级 | ❌ 不引 `sqlite-vec` / FAISS |
| **不需要神经 embedding** | 术语 query 98.8%、口语 query 改写后 **100%** —— 已经到顶，**没有可提升的空间** | ❌ 不引 embedding API / 不落地本地模型 |
| ~~不需要"术语整词"这一层~~ **← 已被第二个语料推翻** | 在 Ceph 上加了 157 个术语整词 token 读数一模一样（98.8%）；**但在计组上把纯中文类从 87.5% 拉到 100%** | ✅ **保留**，见 §13 |
| **需要查询改写** | 唯一有效的语义补丁，口语 query **+7.1pp**（92.9% → 100%） | ✅ 用现有 LLM 做改写 |

> **这张表就是面试答案**：能说清"我评估过 embedding、结论是不需要"的人，
> 比无脑上向量库的人可信得多——**尤其当你手上有 325 + 705 个 chunk 的实测数字。**
> 这与 P2 里"没用 LangGraph，因为循环只有三个状态"是同一种判断。
>
> ⚠️ 但请注意上表第三行：**其中一条结论只在一个语料上成立，被第二个语料推翻了。**
> 详见 §13——这大概是本轮最有价值的一件事。

### 1.4 分词器：三层 token（实测调出来的，不是拍的）

```python
1. 英文/技术术语       _TOKEN_EN   →  CRUSH / pg_num / rados
2. 数字 + 单位阈值     _NUM_UNIT   →  3副本 / 64KB / 0.85      ★ 必须有
3. 中文 2-gram         _TOKEN_CN   →  兜底，任何中文串都能被检索
```

**第 2 层是调试发现的，不是设计出来的。** 第一版探针中文召回只有 **52.5%**，
排查后发现：那 59 条"非英文"query 里只有 **17 条是纯中文**，
其余 42 条是 `3副本` / `0.85` / `64KB` 这类数字术语——
英文正则要求字母开头、中文正则要求汉字，**两边都不匹配 → token 为空 → 必然检索失败**。
补上第 2 层后，中文类 52.5% → 100%，整体 94.5% → 98.8%。

> ⚠️ **同时修了一个评估方法上的坑**：第一版直接 `unique_terms[:600]` 并按长度排序，
> 结果 600 条里 541 条是短英文术语、中文只占 59 条——**中文的低分被平均掉了**。
> 改成**按类型分层采样（每类 200 条）** 后才看见问题。
> 教训：**评估集的构成偏差会掩盖真实缺陷**，和 P1 里"平均 97.7% 掩盖了后段 83.9%"是同一类错误。

## 2. 架构

```
课件（.pptx / .pdf）
  │ ① 复用现有提取器（extract_any，零改动）
  ▼
② 分块：**按页**切，chunk 自带元数据 {file, page, title}
  │     （粒度理由见 §3：页码是引用溯源的最小单位）
  ▼
③ 建索引：BM25 倒排（内存态，11 ms，可落盘缓存）
  ▼
④ 检索：query 改写 → BM25 Top-K → （可选）按节/页过滤
  ▼
⑤ 生成：Top-K 原文 + 强制引用指令 → LLM（**SSE 流式**）
  ▼
⑥ ★ 引用验证器：抽出答案里的引用声明 → 比对被引页原文的术语
  │     → 逐条标注「引用可信 / 引用待核」
  ▼
⑦ 输出：流式答案 + 引用清单（含可信度标记与源页原文片段）
```

### 关键决策（每条都定了"放弃的替代"）

| 决策 | 选择 | 理由 | 放弃的替代及原因 |
|---|---|---|---|
| 检索算法 | **BM25（纯 Python）** | 实测 0.20 ms、召回 98.8%；**零依赖、可离线、可解释**（能指着 IDF 说为什么这页排第一） | 向量检索——见 §1.3，无提升空间；引入依赖与不确定性 |
| chunk 粒度 | **按页** | 引用溯源的最小单位就是页；硬切字数会让一页跨两个 chunk，引用只能给"第 N 页附近" | 固定字数切分（如 512 token）——牺牲引用精度换长度均匀，本场景不值 |
| 中文分词 | **2-gram（不引 jieba）** | 与 `coverage.py` 一致的理由：词典 ~10MB，与"本地小工具"定位不符；实测 2-gram 已到 100% | jieba / HanLP——实测前先别加，实测后更没必要 |
| 查询改写 | **用现有 LLM 改写** | 唯一有效的语义补丁（+7.1pp）；成本极低（一条短 query） | 神经 embedding——**它解决的也是这个问题，但代价大得多且收益已被改写拿到** |
| 流式协议 | **SSE**（`EventSource`） | 单向、纯文本、浏览器原生支持、无额外依赖 | WebSocket——双向是多余的；本项目问答只有"问→答"一个方向 |
| 引用验证 | **术语级比对（复用 coverage.py）** | 与 P1/P2 同源：**零成本、可复现、纯函数**；且这是别家 RAG 没有的一层 | 让 LLM 自查引用——既花钱又不可复现，等于让考生自己批卷 |

## 3. 分块与元数据

```python
@dataclass
class Chunk:
    id: int
    file: str        # 课件文件名（= 简历/文档里说的"节"）
    page: int        # 页码，从 1 开始  ← 引用溯源的最小单位
    text: str        # 该页正文 + 备注（备注常含考点）
    title: str       # 该页的标题行（有则填，用于展示与过滤）
```

- **一页 = 一个 chunk**，不做二次切分。实测 p50 只有 186 字符、max 690，
  远低于任何模型的上下文压力，**没有切分的必要**。
- **元数据必须带 `file` + `page`**：这是"引用可验证"的前提——
  没有页码，验证器就无从比对。
- 术语表**按份课件**挖掘（`mine_cn_terms`），不全局挖——
  同一串词在不同课程里的含义不同，"按份挖"得到的是**本课程的专有名词**，更准。

## 4. 检索

```python
def search(query: str, topk: int = 5, scope: str | None = None) -> list[Hit]
    # scope：可选的文件名过滤（"只在这份课件里找"）——界面上就是"限定到某一节"
    # 返回 [{chunk, score, rank}]，含原文，供引用验证与前端展示
```

- **查询改写**：调用一次 LLM，把口语问句改写成术语式检索式。
  提示词里**必须带上该课的术语表**作为约束——否则改写结果落不进课件的词汇空间
  （探针 §1.2 的改写是"知道答案"的手工版，是乐观上界，落地时要靠术语表把差距补回来）。
- **改写降级**：LLM 不可用时直接用原 query 检索（实测原始口语 query 也有 92.9%）。
  **不因为改写失败就整个问答不可用。**

## 5. ★ 引用溯源与可验证（核心差异化）

### 5.1 生成侧：强制引用

提示词要求每个论断后给 `（源：<文件名> 第 N 页）`，且**只允许引用给定的 Top-K chunk**。
给模型的上下文里，每段都带明确的页码标签，降低它编页码的动机。

### 5.2 验证侧：把「引用」变「可验证」

**实际实现用的是「检索排名」，不是本节最初设计的「术语命中率」。换掉的原因是标定。**

```python
def verify(answer, default_file="") -> list[CitationCheck]
    # 1) 正则抽出所有引用声明 → [(claim, file, page)]，多页写法展开成多条
    # 2) 被引页不在知识库里 → 直接判「未找到该页」（硬事实，可以断言）
    # 3) 被引页在库里 → 把 claim 当 query 在**全库**检索，看被引页排第几（rank）
    # 4) rank ≤ 1 → 引用可信；否则 → 引用待核（附该页原文片段供自查）
```

**两个信号的标定对照**（三组程序化样本，每组 120 条，14 份真实课件）：

| 规则 | 真引用通过 | 假引用通过 | 净区分度 |
|---|---|---|---|
| 术语命中率 ≥ 0.60 | 96.7% | **16.7%** | 80.0pp |
| **检索排名 rank ≤ 1** | **93.3%** | **0.0%** | **93.3pp** |

**为什么术语命中率不行**：同一门课的词汇高度重叠——"Ceph"、"集群"、"节点"几乎每页都有，
命中率被这些通用词刷满，区分不出是哪一页。而 rank 用的 BM25 打分里 **IDF 天然压低了通用词的权重**，
所以它对"这段文字到底是哪一页"更敏感。数据上 rank 分布也拉得很开：

| 组 | rank 中位数 |
|---|---|
| 真引用 | **1** |
| 页码错（同课件另一页） | **106** |
| 内容编造（跨课件） | **249** |

> 术语命中率并未废弃——它仍作为**展示信息**留在结果里（"论断里有几个术语在源页找到了"），
> 只是不参与判定。

**一个刻意的取舍差异（与 P1 相反）**：

P1 覆盖率回检是「**宁可漏报，不可冤枉**」；这里反过来，用**6.7% 的误报换 100% 的假引用检出率**。
因为两者代价不对等：P1 的误报会让用户以为文档不完整、对一个免费功能失去信任；
这里的误报只是"提示核对 + 附上原文片段"，而漏报是**用户采信了编造的内容**。

措辞上仍用「**引用待核**」而非「引用错误」，把最终判断权交回用户——判据只负责缩小范围。

### 5.3 为什么这一层值钱

| | 普通 RAG 项目 | 本项目 |
|---|---|---|
| 引用 | "我给了引用" | "**我能证明这条引用站得住**" |
| 失败时 | 用户自己发现被引页没有那个内容 | 系统主动标出「待核」并给出原文 |
| 与既有能力的关系 | 孤立 | **复用 P1 的判据，把"可验证"从内容延伸到引用** |

> 面试一句话：*"RAG 的引用最容易造假——模型编一个页码你也看不出来。
> 我用术语级比对给每条引用做了自动核验，标出站不住的那些，并把原文片段一并给出。*"

## 6. 流式（SSE）

- 端点：`POST /api/ask`（返回 `text/event-stream`）
- 事件序列：`{"type":"rewrite","query":...}` → `{"type":"sources","hits":[...]}`（**先给引用源，再给答案**）
  → `{"type":"delta","text":"..."}` 多次 → `{"type":"citations","checks":[...]}` → `{"type":"done"}`
- **先推 sources 再推答案**：用户能立刻看到"我找到了哪几页"，不必等生成完——
  这是流式体验里最容易做砸的一点。
- 前端：`EventSource` + `marked` 增量渲染（`marked` 已在 `static/vendor/`，离线可用）。

## 7. 验收标准（事先定死，沿用 P1/P2 的纪律）

| # | 验收项 | 判据 | 状态 |
|---|---|---|---|
| 1 | **检索召回** | 术语 query Recall@5 **≥95%**（分层统计：英文/数字/中文三类都要报） | ✅ **98.8%** |
| 2 | **口语泛化** | 口语 query Recall@5 经改写后 **≥95%** | ⚠️ **改写后的旧读数 100%（n=14）；但真实混合问句的锚点页命中只有 65%** ——见 §21.2，旧样本太小，这个结论要打折 |
| 3 | 延迟 | 检索 ≤50 ms（含改写后的那次检索）｜首 token 延迟 ≤3 s | ⚠️ **未达标**：首 token 中位 **3.28 s**（改写 1.92 s + 检索 1 ms + 生成 1.4 s）。判据不该改，该改的是"改写这一跳" ——见 §22 |
| 4 | **★ 引用可验证** | 标定回归：真引用通过率 ≥80%、假引用通过率 ≤8%（标定值 93.3% / 0.0%） | ✅ 标定 **93.3% / 0.0%**；**真实问答输出上 89.8%**（127 条，见 §21.3） |
| 5 | **★ 有溯源 vs 无溯源对照** | 同一批 20 个问题，要求带引用 vs 不要求，**带引用的答案准确率更高**（人工评分） | ❌ **未通过（未证实）**：两臂严格准确率都是 **80.0%（16/20）**，20/20 题逐题同分、0 对不一致，McNemar p=1.000 —— 见 §21.6 |
| 6 | 单测 | 分块元数据 / 三层 token / BM25 打分 / 引用抽取与判定 / SSE 事件序列 | ✅ 检索层与引用层 52 例 + SSE 28 例；本轮再补 9 例（对照开关不可污染、计时字段） |
| 7 | 成本 | 单次问答成本 ≤ 一次文档生成的 1/10 | ✅ **¥0.0094/次**（20 题 × 2 臂共 ¥0.3741）；单节生成基准 ¥0.13，阈值 ¥0.013 |

> 验收 5 是 P3 的**主张所在**。如果"引用可验证"证明不了价值，
> 那 P3 就退化成一个普通的 RAG demo——**所以这条必须真跑，不能略过。**

## 8. 诚实性约束（与 P1/P2 同级）

1. 引用核验的结论措辞是「**引用待核**」而非「引用错误」——判据是词面的，换说法会误判；
   同时必须附上**被引页的原文片段**，把最终判断权交回用户（沿用 P1 的做法）。
2. **检索命中 ≠ 答案正确**：召回率是检索侧指标，不能拿来宣称"回答准确率 100%"。
3. 术语表挖掘（`mine_cn_terms`）会产生噪声词（如"典型代表"），
   引用验证时**只统计命中，不拿未命中的噪声去指责引用**——宁可少报，不可冤枉。
4. 查询改写的效果**必须分别报"原始"和"改写后"两个数**，不能只报好的那个
   （探针里就是 92.9% / 100% 两个数并列）。

### 12.2 ★★ 五个坑，全部是"真跑"抓出来的

**① 正则的字符类排除了括号 → 三分之一样本抽不出引用（踩了两次）**

第一版 `(?P<file>[^（）()]{0,80}?)`——排除了中英文括号。
而真实课件名里 `Ceph 与 Kubernetes 集成 (CSI).pptx` 含英文括号 →
**三组样本各有 31/29/35 条"未能抽出引用"**，看起来像判据失灵，实际是正则。

改成只排中文括号 `[^（）]` 之后，`Ceph 对象存储（RGW）配置与使用.pptx` 又抽不出来——
**14 份课件里含中文括号的占一半**。这才明白：**不该用字符类排除，该用 `第 N 页` 做右锚点**。
修好后"未抽出引用"归零。

> **教训**：当失败表现为"结果莫名其妙地差"而不是"报错"时，
> 先怀疑**输入没被正确解析**（正则/编码/切分），别急着调判据。
> 这次如果直接去调阈值，会在一个残缺的样本集上永远调不出好东西。

**② 判据存在循环论证 → coverage 恒等于 1**

第一版用**被引页的术语表**去反查论断里的中文术语，再拿这个集合去验证
"论断的术语是否都在被引页"——**假定与结论是同一件事**，coverage 恒等于 1。
换成课术语表做分母才破掉。（改正后术语命中率也仍然不佳，见 ④。）

**③ 限定课件内排名时，单页课件的引用恒等于第 1 名**

`_rank_of` 最初限定在 `scope=file` 内检索。一份只有一页的课件，
引用它**永远"正确"**——判据直接失效（单测 `test_跨课件引用判待核` 抓到）。
改成**全库排名**后不仅修掉这个，还顺带覆盖了"论断其实来自另一份课件"这种错引，
而且**真引用通过率反而从 87% 升到 93.3%**——因为在更大的候选集里排第 1，
比在小集合里排第 1 更有说服力。

**④ "术语太少就放行"的分支 → 假引用通过率被抬到 32.5%**

从 P1 的 `MIN_TERMS_FOR_PERCENT` 抄来的思路：术语少于 2 个时不给结论。
但方向抄反了——P1 那里是**不显示百分比**（沉默），这里我写成了**放行**。
而错引用里恰好有相当一部分是"论断没有可识别术语"的情况（跨课件错引、纯中文短句），
等于**给它们盖章**。诊断时看到一批 `rank=325`（全库排最后）的样本却判"可信"，才定位到。

> **rank 不依赖术语抽取**（它用论断的全部 token），所以这个前置条件本来就不该存在。
> **把一条判据从 A 场景搬到 B 场景时，要重新检查它的每个分支在新场景下的含义**——
> 我搬了"术语够不够"这个条件，却忘了它在原场景里的动作是"沉默"而不是"放行"。

**⑤ 标定与单测的样本构造差异，暴露了 ④**

标定脚本给出假引用通过 **0.0%**，单测给出 **32.5%**。
两个数字对不上时**不能挑一个信**——正是这个矛盾驱动我去逐条打印，
才看见 `rank=325` 却判 supported 的异常行。

### 12.3 标定最终读数（可复现：`scripts/p3_citation_calibrate.py`，固定种子）

| 组 | n | rank 中位数 | 判定 |
|---|---|---|---|
| 真引用 | 120 | **1** | rank ≤ 1 通过 **93.3%** |
| 页码错（同课件另一页） | 120 | **106** | 通过 **0.0%** |
| 内容编造（跨课件） | 120 | **249** | 通过 **0.0%** |

- `RANK_TOLERANCE = 1`，claim 截取 **200 字**（标定过 120/200/300，200 最优：
  120 太短特征不足，300 会把页外内容卷进来稀释特征）
- 编造页码（指向不存在的页）→ 稳定判 `not_found`

### 12.4 已知限制（如实记录，不掩盖）

1. **标定样本是"原样截取"的原文，真实场景是模型复述**——复述会换词，
   rank 会系统性变差。所以 93.3% 是**乐观上界**。
   ✅ **已补测（2026-10-19）**：真实问答输出上引用核验通过率 **89.8%**（127 条），
   比标定低 3.5pp，与"复述换词 → rank 变差"的预判方向一致。见 §21.3。
2. **相邻页共享上下文**（"配置步骤 2/3"与"3/3"）会造成误判，6.7% 的误报主要来自这里。
3. **`rank` 的分母是全库页数**（325），所以"排第 1"的绝对难度随知识库变大而变难。
   一门课 14 份课件时无问题；若知识库扩到几十门课，阈值需重新标定。
4. **中文术语靠课件级频次挖掘**（`mine_cn_terms`），会有噪声词。
   它同时影响展示的 `coverage` 和（v0.9.1 起）判定用的 `COVERAGE_FALLBACK`，
   所以噪声词现在**有可能**参与判定；标定里没有专门测这一点，列为已知缺口。

## 13. ★★ 跨语料泛化验证（P3a · 2026-10-15 晚，第二个语料）

用户在 P3a 完成后放进来**第二门课**：哈工大《计算机组成原理》，39 份 PDF / 705 页。
这构成一次天然的泛化测试——**不同学科、不同格式（PDF）、规模翻倍**。

先用新写的 `scripts/pdf_health.py` 查文字层：**39 份全部可用**（705 页 / 14.6 万字符）。
与 PROJECT.md 里"6 份 PDF 有 4 份文字层损坏"的旧经验相反——**每批新课件都该先跑这个检查**。

### 13.1 结果：两个结论被推翻，一个结论被确认

| 结论 | Ceph（325 chunk） | 计组（705 chunk） | 判定 |
|---|---|---|---|
| 不需要向量库 | 0.20 ms | **0.16 ms** | ✅ 更稳了（chunk 更短） |
| 不需要 embedding | 术语 98.8% / 口语改写后 100% | 术语 99.7% / 口语改写后 100% | ✅ 确认 |
| ~~不需要术语整词层~~ | 98.8% → 98.8%（零收益） | **97.3% → 99.7%** | ❌ **推翻** |
| 引用判据 `rank ≤ 1` | 真引用 93.3% | **真引用 77.5%** | ❌ **推翻** |

### 13.2 第 4 层（术语整词）为什么在计组有用

计组的纯中文术语——`寻址方式` / `指令周期` / `微操作命令`——在 2-gram 下被切成
"寻址/址方/方式"，IDF 被稀释，单靠碎片命不中。整词层把 **纯中文类从 87.5% 拉到 100%**。

成本可以忽略：索引 13→15 ms（一次性）、查询 p50 0.16→0.17 ms、p95 0.22→0.41 ms。
**用亚毫秒延迟换 2.4 个百分点，不值得犹豫。**

### 13.3 引用判据为什么要改成组合信号

`rank ≤ 1` 在 Ceph 上真引用通过 93.3%，换到计组**掉到 77.5%**——
计组的知识点分散在 39 个按章节切分的小文件里，相邻章节内容重叠，
"最像的那一页"竞争激烈得多。而同一个语料上 `coverage ≥ 0.80` 反而涨到 **92.1pp**。

**两个语料各有一个赢家——挑哪个都是过拟合。** 于是改成组合信号并联合标定：

| 规则 | Ceph 真/假 | 计组 真/假 |
|---|---|---|
| rank ≤ 1 | 93.3% / 0.0% | 77.5% / 0.0% |
| coverage ≥ 0.80 | 82.5% / 2.5% | 99.2% / 7.1% |
| **rank≤1 或 cov≥0.80** | **94.2% / 2.5%** | **99.2% / 7.1%** |

两个信号各管一类失败，合起来覆盖更全：
- `rank ≤ 1` —— 管"引用指到了别处"
- `coverage ≥ 0.80` —— 管"术语根本对不上"

用 OR 而非 AND：两者都能独立证明引用站得住，多留一个信号是为了**少冤枉真引用**
（与 P1 的"宁可漏报不可冤枉"一致）。

### 13.4 计组语料的两个新发现

1. **有一对重复文件**：`4.2 主存储器.pdf` 与 `4.2主存储器.pdf`（前者带空格）。
   放进同一个知识库会让同一内容占两票，**建议删掉一份**。
2. **口语 query 的文件级 ground truth 过于严格**：计组里
   "中断是怎么处理的" 命中了 `8.4 中断系统.pdf` 而期望是 `5.5 程序中断方式.pdf`——
   这**不算检索错**，是两个章节都讲中断。单文件正确答案的判据在章节有重叠的课程上会误判。
   → 计组口语召回因此显示 80.0%（15 条错 3 条），改写后 100%。
   **这个 80% 要带着上述限定读，不能当成"检索不行"。**

### 13.5 沉淀下来的方法（可复用的教训）

> **`先量再改` 里的"量"必须是多个语料。**
> 只在一个课程上标定得出的结论，很可能只是**那门课的词汇分布特征**。
> 本轮在一个语料上得出"这层没用、砍掉"，换门课就变成"这层有 2.4pp 的收益"；
> 判据同理——**单一语料的阈值不是阈值，是拟合**。
>
> 这和 P1 的"平均覆盖率 97.7% 掩盖了后段 83.9%"是**同一类错误**：样本代表性不足。
> 区别只是那次是"样本内部分布不均"，这次是"样本只有一个域"。

### 14.3 ★★ 端到端真跑发现的三个问题

#### ① 计组课件是「提纲式」，问答上限受课件文字层限制（最重要）

真跑第一个问题 "cache 是怎么工作的"，模型回答得非常诚实：

> **给出的片段里没有 Cache 工作原理的实质内容。** 唯一涉及 Cache 的片段只是章节目录…

查了原始文字层，确认**模型是对的**：

```
4.3 高速缓冲存储器.pdf 第 1 页：
4.3 高速缓冲存储器
• 一、概述  • 1、为什么用Cache  • 2、Cache的工作原理
• 主存和缓存的编址  • 命中与未命中  • Cache的命中率 …
```

**哈工大这套课件每页只有小节标题，正文讲解在口头**（PDF 又没有"备注页"这个概念）。
所以：**即使检索 100% 准确，也只能回答"这个主题包含哪几个子问题"，答不出"具体是什么"。**

> **这是知识库问答的固有上限：答案的信息量 ≤ 课件文字层的信息量。**
> 与检索算法无关，与提示词无关。要突破只能上整页渲染 + 视觉模型（读图上内容）。
> 对比之下 Ceph 那批 PPTX 有正文段落（`在大型集群扩容中，使用声明式 YAML 文件是运维的最佳实践…`），
> 问答质量会明显更好——**同一套代码，两个语料的上限不同**。

#### ② 检索对**自然语言问句**的表现远差于术语 query（暴露了评估集的盲区）

问 "cache 是怎么工作的"，top5 里 **3 个命中"6.3 定点运算"**；
问 "DMA 是什么"，命中的是发展史、基本组成、浮点表示——**没有一个是对的文件**。

根因是中文 2-gram 产出的**虚词 token**：「是怎么工作的」切出 `是怎/怎么/么工/工作/作的`，
其中 `是`、`什么`、`工作` 这类词在长文档里高频，虽然 IDF 低，**但词频累积后压过了实体词**。

> ⚠️ **这与 §1.2 测出的「术语 query 召回 98.8%」并不矛盾——是评估集的盲区。**
> 那组评估用**术语本身**当 query（`crush` / `3副本`），而术语在课件里的分布正是 BM25 最擅长的情况；
> 真实用户问的是**自然语言**，两者的难度不同。**探针测的是"能不能定位术语"，不是"能不能回答问题"。**
>
> 这与 P2 那条教训同源：**评估方式决定了你能看见什么**。
> 下一步应先建一个**自然语言问句的评估集**（每题标好应在哪几页），再谈改检索。

#### ③ 引用抽取正则的第三个坑：跨引用合并

真实模型的输出里出现连写引用：

```
（源：8.2 指令周期.pdf 第 1 页；源：8.2 指令周期.pdf 第 2 页）
```

file 段当时是 `.`（任意字符），于是**两条引用被吞成一条**——
file 变成 `8.2 指令周期.pdf 第 1 页；源：8.2 指令周期.pdf`，页码取最后一个。
表现是**三条真引用被判「未找到该页」**。

修法：file 段排除 `；;\n`（引用之间的分隔符），结尾改用 **lookahead**
（一条引用的结束可能是 `）`，也可能是分号，还可能是行尾——不能强制要求闭括号）。
同理加了两条回归测试。**这是同一个正则的第三次迭代**，三次都是"真跑"抓出来的：

| 版本 | 排除了什么 | 怎么坏的 |
|---|---|---|
| ① `[^（）()]` | 中英文括号 | `(CSI).pptx` 抽不出 |
| ② `[^（）]` | 中文括号 | `（RGW）.pptx` 抽不出 |
| ③ `.` | 无 | 跨引用合并 |
| ④ `[^；;\n]` + lookahead | 分隔符 | ✅ 当前 |

#### ④ 重复文件的危害被实证

`4.2 主存储器.pdf` 与 `4.2主存储器.pdf` 在 "DMA 是什么" 的检索结果里**同时出现，score 完全相同（10.2216）**——
同一内容占两票，还挤掉了本该命中的页。**再次建议删掉一份。**

### 14.4 已知限制（新增）

1. **问答质量的上限 = 课件文字层信息量**（见 ①）。提纲式课件上，这个功能只能做"定位到哪一节"，
   不能替代讲解。**界面上应如实提示**，而不是让用户以为"答不出 = 工具坏了"。
2. **自然语言问句的检索质量未被系统评估**（见 ②）。当前所有召回数字都来自术语 query 与
   15~16 条口语 query，**样本不足以支撑"检索够用"的结论**。
3. **同课相邻页互相抢分**：Q3 里 `8.2 指令周期.pdf` 第 1/2/3 页同时命中且内容高度重叠，
   top-5 里三页来自同一份课件——**上下文被稀释**（其余两份课件的信息进不来）。
   `topk` 的分配策略（按文件限额）是待验证的改进方向。

## 15. ★★ 对照实验：两位老师的同一门课（P3b 续 · 2026-10-15 晚）

用户提了一个很尖锐的问题：

> "如果一个老师的风格是像这样自己讲解的话，我们的助手就很有限了，无法达到复习的效果。"

恰好他又找来**另一个老师的计算机组成原理课件**（9 份 `.ppt`），于是构成一次天然对照：
**同一门课、两位老师、两套课件**。

### 15.1 前置：`.ppt` 旧格式需要转换

新课件是 `.ppt`（复合文档二进制），python-pptx 读不了，项目也明确不支持。
本机装了 PowerPoint（COM 版本 16.0），于是写了 `scripts/convert_ppt.py` 走自动化批量转。

**9 个文件全部转换成功，每个 < 1.5 秒。**

> **为什么单独成脚本、不塞进 extractor**：`.ppt` 是**导入期的一次性动作**，
> 不是每次提取都要做的事。塞进 extractor 会让**每次提取都去探测 COM**，
> 而 PowerPoint 没装、被安全软件拦、进程残留……都会变成提取失败。
> 转换产物与源文件并列，之后所有流程只认 `.pptx`。

### 15.2 文字层对比（★ 一个指标被证伪）

| | 计组（哈工大，39 PDF） | 第四版（9 PPTX，转换后） |
|---|---|---|
| 页数 | 705 | 986 |
| 总字符 | 145,027 | 144,641 |
| **每页平均字符** | **206** | **147** |
| 术语数 | 807 | 1,722 |

**每页字符数是误导性的——第四版反而更少。** 看实际内容才明白：

| | 哈工大 | 第四版 |
|---|---|---|
| 第 1 页 | `4.3 高速缓冲存储器` + `• 一、概述` + `• 1、为什么用Cache` … | 章节导语段落：`存储系统是由几个容量、速度和价格各不相同的存储器构成的系统…` |
| 特征 | **目录标题 + 图注**（页面字符多是因为示意图的标注文字被一起提取） | **叙述性段落 + 要点**，还有**「本章学习要求」页**（了解/理解/掌握） |
| 叙述密度 | 低（没有成句的讲解） | **高**（有成段的解释性文字） |

> **正确的指标不是"每页多少字"，而是"有没有叙述性段落"。**
> 哈工大那套字多，但都是标题和图注——**字多≠有内容**。
> 这提醒了一件事：**做语料评估时不能只看字符数这类代理指标**，
> 必须实际翻开看（这次只花了两分钟看第 1 页，就避免了一个错误结论）。

### 15.3 问答对比：差异是实质性的

同一组问题（`cache 是怎么工作的` / `DMA 是什么` / `指令周期分为哪几个阶段`）。

**Q1「cache 是怎么工作的」**：

| | 哈工大 | 第四版 |
|---|---|---|

### 15.4 ★★ 最重要的发现：改写是否生效 = 检索质量的第一变量

Q1 在哈工大语料上**跑过两次**，结果完全不同：

| 第几次 | 改写 | top-5 命中 |
|---|---|---|
| 第一次 | **未生效** | **3/5 是错的**（命中"6.3 定点运算"） |
| 第二次 | **生效** | **5/5 全对**（全是 4.3 高速缓冲存储器） |

**同一个问题、同一个模型、同一个语料——只有改写是否生效这一个变量在变。**
而模型对改写**不稳定**（temperature 已设为 0）。

Q2 更典型：

| | 改写 | 检索 | 答案 |
|---|---|---|---|
| 强化前 | 未生效 | 命中发展史/基本组成/浮点表示，**没有 5.6** | 「**课件这部分没提到 DMA**」 |
| 强化后 | **生效** | 命中 **5.6 DMA方式 第 2/7/5 页** + 5.1 概述 | **完整的 DMA 特征 + 三种交换方式 + 周期挪用情形** |

**修法是纯提示词的**（零成本）：加 few-shot 示例，并把要求从"替换口语说法"改成
**"即使原问题已有关键词，也必须在它基础上补充相关概念词"**。

效果：**改写生效率 1/3 → 2/3**。剩下那个（`指令周期分为哪几个阶段`）不改写也**已经全对**——
它本身就是术语式查询。

> **这条比"要不要上 embedding"重要得多。** 检索层的算法（BM25 / 向量）
> 决定的是**天花板**，而改写决定的是**你有没有走到那个天花板下**。

### 15.5 回答用户最初的问题

> "如果老师的风格是自己讲解，助手就很有限了，无法达到复习的效果。"

**部分成立，但比预想的好。** 准确的说法是：

- **提纲式课件**（哈工大）：助手能给出「这一节讲什么、有哪几个要点、图里画了什么」级别的答案，
  **给不出概念的定义与推导**。用户仍需回到课本——但至少不用翻几十份 PPT 找位置了。
- **有叙述的课件**（第四版）：助手给出的是**可直接背诵的复习材料**。

**分界线是"课件文字层里有没有叙述性文字"，而不是"老师讲不讲"**——
老师口头讲的如果没进 PPT，程序就看不见（PDF 又没有"备注页"这个概念）。

> **对策**：界面上应如实区分这两种情况。当检索到的片段"术语密度高但叙述密度低"时，
> 提示用户"**这份课件的文字层以提纲为主，答案可能不完整，建议对照课本**"——
> 而不是让用户以为"答不出 = 工具坏了"。
> **要真正突破，只有整页渲染 + 视觉模型这一条路**（读图上内容），
> 那属于 P4 的范围。

## 16. 前端追问框（P3b 收尾 · 2026-10-15 晚）

### 16.1 位置：整课批量的选文件区下方

追问框挂在**「整课批量」tab 里、文件选择区的下方**，而不是单份模式。
理由：知识库的输入是**一门课的一批课件**，而那正是这个 tab 已经在收集的东西。

**但知识库与"生成"完全解耦**——用户选完课件可以直接提问，不必先跑一遍批量生成。
这也是把知识库建在**课件原文**上带来的直接好处。

### 16.2 三个关键决策

| 决策 | 选择 | 理由 |
|---|---|---|
| **区块常驻显示**（不去监听文件选择变化） | 区块一直在，点了才发现没选课件 | 监听要改三四处现有代码（加文件/删文件/清空/重排），**容易漏且侵入性大**；"按钮出现又消失"对用户也更难预期 |
| **文件指纹自动重建** | 提问前比一次 `文件名:大小` 指纹，变了就重建库 | 同上——把判断集中在一处，不动 `batchFiles` 的任何现有写入点。`kb_id` 本来也由文件属性哈希而来，语义一致 |
| **POST + `ReadableStream` 手工解析 SSE** | 不用 `EventSource` | 浏览器原生 `EventSource` **只支持 GET**，而问答参数（kb_id / question / scope）塞进 query string 既难看又有长度限制。手工解析约 30 行，换来 POST、JSON body、可中止 |

### 16.3 建库接口的形态变更（实现时才发现的）

原设计是 `POST /api/kb` 接收**文件路径列表**（复用 `uploads/` 里已有的文件）。
实现时发现**这条路走不通**：

> 单份模式的 `/extract` 会把课件留在 `uploads/`，
> 但**批量模式的 `/batch/peek` 用的是 `tempfile.TemporaryDirectory()`——提取完就删**。
> 前端在批量 tab 里选好的文件，**服务端并不存在**。

于是改成 `POST /api/kb` 直接接收 **multipart 上传**，自己存到 `uploads/<id>/` 再建库。
**只上传这一次**——之后所有问答只传 `kb_id`，靠 `output/kb/<kb_id>/` 的缓存服务。

同时加了文件数上限（80）与格式校验（只收 `.pptx` / `.pdf`），
并把被拒文件与提取失败**一并在响应里如实报出**。

### 16.4 两个容易踩的细节

1. **`decoder.decode(value, {stream: true})`** —— `stream: true` 必须有。
   中文是多字节字符，**可能正好被切在 chunk 边界上**；不加这个选项，
   跨边界的字会解成乱码（表现为答案里零星出现"口"字）。
2. **流式渲染要节流**：每个 delta 都 `marked.parse` 一次会把长回答卡住。
   做法是**间隔 80ms 才重渲染一次**，并在 `citations` / `done` 时补一次完整渲染。

另：引用核验的每条结论都带 `<details>查看源页原文</details>`——
核验结论一律叫「待核」而非「错误」，**必须把证据一并给出**，否则用户无从核对（§8 的诚实性约束）。

### 16.5 验证方式（三层，逐层加严）

| 层 | 手段 | 抓到什么 |
|---|---|---|
| 1 | 抽出内联 JS 跑 `node --check` | 语法错误 |
| 2 | 比对 HTML 定义的 `id` 与 JS 引用的 `id` 的**差集** | ID 拼错（运行时报 null，最难查的低级错误） |
| 3 | **`scripts/smoke_qa_api.py`**（起真服务 + 真模型） | 契约错误：multipart、SSE 帧格式、事件顺序 |

第 3 层的实测输出：

```
✓ kb_id=3f6ea917fc56  3 份 / 42 页 / 7,888 字符
[2.1] DMA 是什么

  命中 5 页：5.6 DMA方式.pdf p5、p7、p2
  首 token 4.9s / 全程 7.4s
  答案 913 字：「课件这部分没提到「DMA 是什么」的定义或全称」
  引用核验：3 条可信 / 1 条待核

```

> 注意那句答案：**哈工大那份课件确实只有 DMA 的工作机制、没有定义**，
> 模型如实说了"没提到定义"而不是编一个——
> §8 的诚实性约束（"只在给定材料范围内回答，鼓励说没有"）在真实链路上生效了。

## 17. 问答历史（2026-10-17）

### 17.1 需求与判断

用户实测后提出：**"要不要单独给历史记录一个页面？把文档生成记录和提问记录都放进去。"**

**判断：该做，但"合并成独立页面"这个形态不建议——而且当时缺的不是页面，是数据。** 三条理由：

1. **提问记录当时根本没落盘。** `output/kb/<kb_id>/` 里只有索引缓存，问过什么、答了什么，一个字都没存。
   做页面之前得先有数据，否则是在猜形态。
2. **两类记录性质不同**，按时间混排反而互相干扰：

   | | 文档生成记录 | 提问记录 |
   |---|---|---|
   | 产物 | **文件**（总册/单份文档，能下载重看） | **对话**（问答文本） |
   | 有价值的信息 | 哪门课、几节、何时生成 | **问过什么、答得怎么样** |
   | 混排后果 | 找"上次那份总册"被一堆提问淹没 | 反过来也一样 |

3. **提问记录的价值比"查找"大得多**：复习场景下，**你问过的问题 = 你不会的地方**。
   按主题归组就是一份自动生成的**薄弱点清单**——哪一章问得最多、哪些概念反复问，
   那就是该优先复习的地方。只做成"历史列表"的话，这个数据就浪费了。

### 17.2 本次做了什么（分三步走的第一步）

**落盘**：`output/qa/<kb_id>.jsonl`，一条一行。

| 决策 | 理由 |
|---|---|
| **不放在 `output/kb/` 下** | 那里有 72 小时 TTL（`KB_TTL_HOURS`）。用户可能一周后才回来翻"上次问了什么"，那时知识库缓存早已过期，但历史必须还在 |
| **jsonl 追加**，不读写整个 JSON | 历史会越来越长，为一条新记录重写全文不划算 |
| **答案存全文** | 回看时最想看的就是"上次怎么答的" |
| **写失败不抛异常** | 不能因为写历史失败，让用户已经拿到的答案变成一次失败 |
| **坏行跳过**，不丢整份 | 手工编辑或写一半断电都可能产生坏行，为一行丢掉全部历史不划算 |
| **「问了但没找到」也记** | `no_hit: true`——它说明这个问题在课件里没有落点，要么问偏了，要么课件缺这块 |

**接口**：`GET /api/kb/{kb_id}/qa?limit=N`（倒序，最新在前）。

> 这个接口**刻意不检查知识库缓存是否还在**：历史与缓存是两回事（见上表第一行）。
> 代价是前端拿到历史后若要重问，得先触发一次重建——那是前端的责任。

**前端**：问答区下方多一块「这门课问过的问题」，点一条直接重问。

### 17.3 还没做的（等数据）

- **独立历史页面**：等问过 30+ 个问题再做，让数据决定形态（是要"按时间"还是要"按课程"？）
- **按主题聚合的薄弱点清单**：这才是这份数据真正值钱的地方，但需要先有量

### 17.4 ★ 顺带修的一个真 bug（真跑抓到）

重启服务跑端到端时，**建库直接 500**。查日志：

```
File "app/api/routes.py", line 61, in _cleanup_stale_uploads
    shutil.rmtree(entry, ignore_errors=True)
File ".../shim/sitecustomize.py", ...
SystemExit: 1
```

**根因**：`_cleanup_stale_uploads()` 只 `except OSError`，而本机安全 shim 把"拒绝删除"
实现成了 **`SystemExit`**——它**不是 `Exception` 的子类**，所以一个都没抓住。

但比这个环境特例更重要的是它暴露的**设计缺陷**：
**清理是纯副作用，任何失败都不该拖垮上传/建库这条主流程。**
磁盘满、权限不足、文件被占用（Windows 上很常见）都会触发同类失败，
而原来的写法会让"删一个过期文件失败"变成"整个请求 500"。

**修法**：整个清理函数包一层，内部每处删除也逐个兜住：

```python
def _cleanup_stale_uploads() -> None:
    try:
        _cleanup_stale_uploads_inner()
    except (OSError, SystemExit):
        pass
```

> 教训与 P2 那条同源：**"失败了也不报错"的路径要专门验证**。
> 这里反过来——**一个"失败了就报错"的辅助动作，不该有权毁掉主流程**。

| 端到端 | 真跑 2 个问题 → `output/qa/ba8e790e25c0.jsonl` 生成 → API 读回 **2 条、倒序、字段完整** |

## 18. 历史记录按课程归组（2026-10-17 续）

### 18.1 需求与形态

用户的原话是「要不单独给历史记录一个页面，把文档生成记录和提问记录都放进去」。
我建议的形态是**按课程归组**（一门课 = 它的文档 + 它的问题），而不是按时间混排：

| | 复习文档 | 提问记录 |
|---|---|---|
| 产物 | **文件**（能下载重看） | **对话** |
| 找它时想的是 | "上次那份总册在哪" | "这章我问过什么" |

按时间混排，找文档会被一堆提问淹没，反过来也一样。
而按课程归组之后，**跟人回忆的顺序一致**：先想起"计算机网络"，再想起"那次生成的"或"我问过的"。

不做独立页面的理由：数据量还没到需要分页/搜索的规模，而且
`batchHistory` 区块本来就在做文档记录——**要补的是归组维度，不是新页面**。
形态由一个入口承载，等记录攒到几百条再谈独立页。

### 18.2 ★ 归组的 key 只能是课程名，文件名不行

这是本轮最容易做错的一处，**实际数据直接把"用文件名集合匹配"这条路证伪了**：

| 观察 | 后果 |
|---|---|
| 计算机网络那 3 个批量任务，job **全叫 `讲义.pptx`** | 文件名既分不出课程，也归不了组 |
| 计组的问答记录（`4.3 高速缓冲存储器.pdf` 等）**没有对应的批量任务** | 想靠 batch 反查课程，查不到 |

所以课程身份必须由用户显式给出，并且**跟着数据一起落盘**：

- `KnowledgeBase.course_name`（建库时 `Form` 字段，前端复用「课程名称」输入框）
- `batch.json` 的 `course_name`（本来就有）
- `output/qa/<kb_id>.jsonl` 每条记录新增 `course_name`

### 18.3 提问记录的课程名：四级推导

| 级 | 依据 | 可靠性 |
|---|---|---|
| 1 | 记录自身的 `course_name` | 事实 |
| 2 | 同一 `kb_id` 的其他记录 | 事实（同 kb ⇒ 同文件集合 ⇒ 同课） |
| 3 | **文件集合完全相同**的记录（≥2 份才用） | 高（给历史补漏，见 18.4） |
| 4 | 都没有 → 「未归类」 | **不猜** |

第 3 级**只收 2 份以上**的集合是刻意设限：单份课件常被统一命名（`讲义.pptx`），
不同课程会撞在一起，那时按文件集合推断会**归错课**——归错比不归更糟，用户会以为课件被弄混了。

### 18.4 ★ 意外抓到的真 bug：kb_id 含 mtime，导致缓存从不命中

写归组时开始依赖 `kb_id` 的稳定性，一测就露馅：**同一份文件两次建库得到两个 kb_id**
（`1fcb2694ef42` vs `19ad053014bd`）。

根因：原指纹是 `文件名|大小|mtime`，而问答链路的输入是**上传副本**
（`uploads/<upload_id>/xxx.pdf`），副本的 mtime 恒等于"写入时刻"——每次都不同。
后果是三重的：

| 后果 | 表现 |
|---|---|
| 缓存永不命中 | 每次建库都重付 7 秒提取（39 份 PDF） |
| 历史归组失效 | 每条提问记录各挂一个 kb_id，互相带不出课程名 |
| 目录堆积 | 每次建库新建一个 `output/kb/<id>/`，72 小时后才清 |

修法：指纹改成 `文件名|大小|内容哈希`。读一遍的成本（21MB 约 50ms）相比提取（7s）可忽略，
而且能正确区分"同名同大小但内容不同"的文件。

**这个 bug 从 P3b 上线起就存在，但一直没被发现**——因为此前没有任何功能依赖 kb_id 跨会话稳定：
单次会话里 `qaKbId` 是前端内存里的值，重复建库也会命中同一个缓存（同一次上传的副本 mtime 不变）。
**是"开始依赖某个标识符"这件事，让这个缺陷变得可见。** 回归测试见 `tests/test_kb.py`。

修复前写入的记录挂着旧 kb_id，永远对不上新的——这就是第 3 级推导存在的原因。
实测：用当初那 3 份课件重新建库并提问一次，**4 条记录（含 2 条旧 kb_id 的）全部归到《计算机组成原理》**，`n_unfiled: 0`。

### 18.5 界面上的三个判断

| 决策 | 理由 |
|---|---|
| 「未归类」**永远沉底** | 它是"不知道属于哪门课"，不是"最新发生的"。按时间顶到第一位，用户每次打开第一眼看到的都是一坨不认识的东西 |
| 默认**只展开最新一门** | 全部展开一屏铺满，全部折叠又要多点一次才能看到最近在做的事 |
| 点历史提问 → **就地展开那次的答案**，不是重问 | 重问要求知识库缓存还在（72h），而历史的意义恰是"过很久还能翻"。只读已存答案：零依赖、零成本、永不失败 |

### 18.6 验证

| 层 | 结果 |
|---|---|
| 单测 | **288 passed + 1 skipped**（新增 31 个：归组 15 / 指纹与课程名 11 / 落盘 2 / 其他 3） |

## 20. 已确认的三个问题（2026-10-15 用户拍板）

1. **问答范围**：**整门课跨文件**（如计算机网络那门课的 14 份课件）。
   → `scope` 默认不限定；界面上提供"只在这一节里找"的可选过滤。
2. **入口形态**：**追问框**。
   > ⚠️ 但用户当时的理由里有一条误解需要更正：「如果不先生成文档，知识库中是不是没有相关知识？」
   > **不是。知识库建在课件原文上，不建在生成的文档上。** 三个理由：
   > ① 课件是原始真相，生成的文档是二手转述，本身就有遗漏（P1/P2 就是在治它）——
   > 建在文档上等于把"生成的遗漏"固化成"课件里没有"；
   > ② 引用必须能指回源课件的页码，用户才能拿着去核对，引用到生成的文档则无从核对；
   > ③ 文档是"一份输出"，知识库是"一份资产"，后者应在课件上传时即建好。
   > **追问框只是 UI 位置，索引不依赖它**——顺带白赚一个好处：
   > 只想问几个问题的课件，不用等生成完文档就能问。
3. **改写开关**：**默认开**。界面上标出"已改写为：……"以便用户理解检索结果为何与字面不同；
   LLM 不可用时自动降级用原 query（原始口语 query 也有 92.9% 召回）。

## 21. 验收 5 实验：有溯源 vs 无溯源（2026-10-19）

### 21.1 实验设计

**要证明的东西（假设，不是结论）**：强制引用不只是"好看"，它让答案更准。
> ⚠️ 这个假设**没有得到支持**——见 §21.6。先别急着往下读，把结论放在前面：
> 两臂准确率相同，原因是题集太容易 + 检索缺失吃掉了可比较样本。
**怎么证**：同一批问题、同一份语料、同一个模型，只改引用约束，看准确率。

| 受控项 | 做法 | 为什么必须这么控 |
|---|---|---|
| 检索结果 | **改写只做一次，两臂共用同一个 `RewriteResult`** | 两臂各改一次的话，差异里会混进"改写随机性 → 检索运气"，测的就不是引用了 |
| 代码路径 | 两臂都走 `qa.answer_from_rewrite`，只差 system prompt | 保证除引用约束外没有第二处差异 |
| 生成参数 | model / max_tokens / 关思考，全部一致 | — |
| 诚实性约束 | 两臂都保留"只使用给定片段 / 允许说没提到" | 否则分不清差异是引用带来的还是"不许编造"带来的 |

为了这件事只加了一个参数：`answer_stream(..., require_citation=False)`，
它只服务实验，生产链路永远走默认值（单测钉住了"两臂只差 system prompt"）。

**评估集**：`eval/citation_ab/questions.json`，20 题（**术语型 11 / 口语型 9**），
全部选自 `课件/` 的 14 份 Ceph 课件（325 页），每题标了「答案所在页」+「3 条评分要点」。
不是先有答案再凑题：题目是从**页面内容**倒推出来的，锚点页是逐页读过之后定的。

**关于盲评——只能说清楚一半**：

- **做到的**：每题 甲/乙 的顺序按固定种子随机，避免"总是先看的那条分高"。
- **做不到的**：**没法隐藏哪条带引用**——引用就写在答案里。
  防偏袒只能靠评分规则：**只看事实是否与原文一致，忽略格式、长度、有无引用标注**。
  这条写在评分表顶部，也是这份记录的诚实边界。

### 21.2 ★ 顺带测出来的检索读数（旧结论被削弱）

20 题在 top-5 里的命中情况：

| 题型 | 锚点页命中 | 同一份课件命中 |
|---|---|---|
| 术语（11 题） | **9/11（81.8%）** | 10/11（90.9%） |
| 口语（9 题） | **4/9（44.4%）** | 8/9（88.9%） |
| 合计 | **13/20（65.0%）** | 18/20（90.0%） |

**它说明什么**：失败几乎都发生在"**找对了课件、找错了页**"。
口语题的 9 题里有 4 题属此类（同文件命中 8/9，锚点命中只有 4/9）。

**为什么这不与 §1 的 98.8% 冲突，但足以让那个数打折**：

| | 旧读数（§1） | 本次 |
|---|---|---|
| 判据 | query 里那个术语**有没有出现在命中的页** | 是否命中**标定的那一页** |
| 语料 | 单一门课的 325 chunk | 同一批 325 chunk，但题目跨 14 份课件 |
| 问句 | 术语 query | 术语 + 真实口语混合 |

同一个"召回"，两种判据测的不是一回事。**在用户体验层面，"材料没进来"就是答不对**，
所以验收 2（"口语改写后 ≥95%"）必须标注为**样本不足的旧结论**，不能拿它当"检索够用"的证据。
改进方向已在 §14.4-3 记着（同课相邻页抢分、按文件限额），这次的数据给了它一个更硬的理由。

### 21.3 引用核验的真实场景读数（补 §12.4-1 的空缺）

引用臂 20 题共产生 **127 条引用**：

| 判定 | 条数 | 占比 |
|---|---|---|
| 可信 supported | 114 | **89.8%** |
| 待核 weak | 13 | 10.2% |
| 未找到 not_found | 0 | 0 |

- **89.8% ≥ 80%**（验收 4 的门槛），但比标定的 93.3% 低 3.5pp。
  方向与预判一致：标定样本是原文原样截取，真实输出是模型复述，复述换词会让 rank 变差。
- **"未找到 0"** 说明模型没有编造不存在的页码——它只在给定的 5 页里挑。
- **引到锚点页的题 = 13/20**，与检索命中数完全相同：**引用忠实反映了检索结果**，
  引用层没有额外制造错位（它只判断"这句站不站得住"，不改变去了哪一页）。

### 21.4 客观读数（不含人工评分）

| 指标 | 有引用 | 无引用 | 说明 |
|---|---|---|---|
| 答案长度（中位） | 662 字 | 447 字 | **不是中立的差异**：引用臂长 48%，既更可能覆盖要点，也更可能多写错一句 |
| 首 token（中位） | 1.46 s | 1.10 s | 同一份检索、同一份上下文，差别来自生成更长 |
| 实际生成条数 | 127 条引用 | 0 条 | 对照开关确实生效（无引用臂一条都没标） |
| 总成本 | ¥0.3741（40 次生成 + 20 次改写） | | 单次问答 **¥0.0094** |

> 长度差异是这次实验最需要警惕的混杂因素。评分时若按"内容更全"给分，就会系统性偏向引用臂。
> 所以判据只问：**关键事实对不对、有没有原文没有的陈述**。

### 21.5 人工评分（唯一未完成的环节）

|---|---|

## 22. 首 token 3.3 秒花在哪（2026-10-19）

### 22.1 为什么要拆开量

验收 3 写的是「首 token ≤ 3 s」，§16.5 实测 4.9 s。两个自然的反应都是错的：
**直接把判据改成 5 s**（改判据迁就实现），或**直接去优化生成**（可能根本不在生成上）。

链路里首 token 之前其实有两段：**改写那次完整的 LLM 调用**（非流式，必须等整条检索式生成完）
和检索（毫秒级）。所以先给事件加上四段计时：
`rewrite_ms` / `retrieve_ms` / `first_token_ms`（从请求开始算）/ `total_ms`。

### 22.2 读数（5 题 × 改写开/关，`scripts/qa_latency_probe.py`）

| 项 | 中位数 | 范围 |
|---|---|---|
| 改写 | **1,918 ms** | 606 – 2,060 ms |
| 检索 | 1 ms | — |
| 首 token（改写开） | **3,277 ms** | 2,244 – 4,175 ms |
| 首 token（改写关） | **1,442 ms** | 867 – 1,452 ms |
| 生成首 token（估算） | 1,612 ms（开）/ 1,441 ms（关） | — |

（20 题那次对照实验里改写中位 1,198 ms、首 token 中位 1,460 ms——时段不同差一倍，
**改写这一跳的波动本身就是问题**，它不是稳定的 1.9 s，而是 0.6–2.1 s。）

### 22.3 结论

1. **首 token 超标的元凶是改写那一跳**，不是生成。关掉改写后首 token 中位 1.44 s，判据达标。
2. 术语表不是原因：这门课只有 **157 个术语 / 714 字符**（≈500 token 输入），
   压缩术语表省不出 1 秒——**别在这里优化**。
3. 改写的耗时是**结构性**的：它要等一条完整检索式生成完才能拿去检索，
   天生无法流式、无法与检索并行（有依赖）。

### 22.4 三个可选改法（都还没做，先记下取舍）

| 改法 | 收益 | 代价 / 风险 |
|---|---|---|
| **A. 立即推一条 `status` 事件**（"正在改写…"），改写完再推 sources | 感知首反馈 <100 ms | 只改体验，不改真延迟；要动 SSE 协议与前端 |
| **B. 先用原 query 检索并推 sources（0.2 ms），改写完成若结果不同再推一次修正** | 用户几乎立刻看到"我在哪几页找" | 前端要支持 sources 更新；两次 sources 可能让用户困惑 |
| **C. 按需改写**（query 已命中 ≥N 个术语就跳过） | 术语型问题直接省掉 1.9 s | 要实测召回代价；"什么时候算够"又是一个待标定的阈值 |

**不建议**：把判据从 3 s 改成 5 s。那是把"没做到"写成"做到了"。

**建议**：判据本身拆成两条更贴用户感受的——
「**感知首反馈 ≤ 300 ms**」+「**答案首 token ≤ 3 s**」。
后者在关改写时已经达标，前者正是现在缺的（1.9 s 里界面一片空白）。这属于**重新定义体验指标**，
必须与旧的"未达标"记录并列写，不能覆盖。

规则是**只看事实与原文是否一致，忽略长度、格式、有无引用标注**；
原始记录见 `output/eval_citation/scores.json`（由 `scripts/p3_ab_import_txt.py` 从人工记录导入）。

|---|---|---|---|
| **严格准确率（2 分）** | **80.0%**（16/20） | **80.0%**（16/20） | **0.0 pp** |
| 部分准确（1 分） | 5.0%（1 题，q15） | 5.0%（1 题，q15） | 0.0 pp |
| 错误（0 分） | 15.0%（3 题：q06 / q16 / q19） | 15.0%（同上 3 题） | 0.0 pp |
| 编造率 | 未评（评分时未勾选该维度） | 未评 | — |

配对检验：**不一致对 0 对**（20 题逐题同分），McNemar p = 1.000。
（0 对不一致时这个检验没有信息量——不是"显著无差异"，是"没测到差异"。）

**★ 准确率完全由检索决定，与引用无关**：

| 分组 | 题数 | 结果 |
|---|---|---|
| 锚点页**命中** top-5 | 13 | **两臂全部得 2 分**（13/13） |
| 锚点页**未命中** | 7 | 两臂同分：3 题都判 0（q06/q16/q19，答案都写"课件没提到"）、1 题都判 1（q15）、3 题靠相邻页答对 |

这两个数字合起来说明一件事：**凡是材料进到上下文里的题，模型本来就答得对（天花板）；
凡是材料没进来的题，两臂拿到的上下文完全相同，必然同分。** 题集没有给引用约束留出任何差异空间。

#### 判定

**验收 5 未通过（未证实）。** 按事先写死的判据（"带引用的准确率更高"），
0.0 pp 不构成通过。三条原因按贡献排序：

1. **天花板效应**（主要）：13 道命中题两臂全对——这份 Ceph 课件的文字层叙述充分，
   模型不需要"被逼着找依据"也能答对。要测出引用约束的作用，题目必须是**模型容易答错**的那类。
2. **检索缺失**（次要但更值得修）：7/20 题锚点页没进 top-5，两臂在这 7 题上必然同分。
   这把可比较的样本从 20 压到 13。
3. **单次生成、n=20**：模型随机性没有被平均掉。

#### 不能写进简历的一句话

> ❌ "强制引用让答案更准确" —— 本实验没有支持这个说法。

**能写的**（都有数据）：

- 每条论断带页码引用，**真实问答输出上引用核验通过率 89.8%**（127 条，未找到 0 条）；
- **引用层不制造错位**：引到锚点页的题数（13/20）与检索命中数（13/20）完全相同；
- 单次问答成本 **¥0.0094**，约为单节文档生成（¥0.13）的 7%。

#### 要继续验证的话

| 方案 | 做法 | 前提 |
|---|---|---|
| **换更难的题集**（首选） | 挑跨两页才能拼出答案、含具体数字/命令、易混淆的相近概念 | 题目要先证明"模型裸答会错"——**先跑一遍无引用臂，答对率 >80% 的题直接淘汰** |
| 换指标 | 主指标改成「无出处断言率」（引用臂每条论断都应有出处） | 这是**新判据**，必须事先声明并重跑，不能拿旧数据改算 |
| 提高功效 | 每题重复 3 次取多数、题量 40+ | 成本约 3–4 倍（¥1.2–1.5） |
